# UBER LOG (V1.2) - 配達ダッシュボード & 地雷DB

Uber Eats配達員向けの実運用ダッシュボードおよび意思決定支援システムです。
単なる勤怠管理や会計監査ではなく、**「稼ぎの実態を正しく把握すること」** と **「実走経験から地雷案件・地雷方面・地雷施設を蓄積し、今後の受注判断に活かすこと」** を主目的として設計されています。

---

## 1. 基本思想

1. **実態把握が最優先**
   - 「今週いくら稼げているか」「実質時給はいくらか」を一目で把握できるダッシュボードを提供。
   - 細かな監査（端数突合など）は補助機能とし、主要UIの視認性を邪魔しない。
2. **継続可能なUI（入力負担の徹底排除）**
   - 配達完了はワンタップ（1タップ記録）。
   - 稼働時刻の記録・修正は原則「30分単位」のセレクトボックス選択。秒はUI上に一切表示・入力させない。
   - 時刻が「9時頃」などの本人口頭記録である場合は、推測で確定値化せず「概算時刻（〜頃）」として保持・明示。
3. **地雷DBは「育てるDB」**
   - 単なる固定拒否リストではなく、評価ステータスを **【確定地雷 (AVOID)】** / **【地雷候補・要検証 (VERIFY)】** / **【問題なし (OK)】** の3段階で更新・蓄積する。
   - 施設タイプ（タワマン、商業施設、大型ホテル等）は分類情報とし、一律拒否ではなく個別スポット・実走経験を評価対象とする。

## 2. 稼働時間・実質時給の仕様

### 複数セッション制（何部でも追加・休憩可能）
- 1日の稼働を1回限りとせず、午前の部・午後の部・ブレーキ修理後など、何部でもセッションを追加・編集・削除可能。
- `workSessions: [{ id, start, end, isApproximate, note }]`
- **休憩時間は実質稼働時間から完全除外**。純粋な稼働セッションの合算時間のみを分単位で算出。
- **実質時給** = `総売上 ÷ (実質稼働時間[分] / 60)` で自動算出。

### 30分刻みUI & 秒の完全排除
- 稼働時刻の手動入力・修正は、30分単位（`09:00`, `09:30`, `10:00`...）で選択可能。
- 秒（`:00`）はUI上およびセレクトボックスに一切表示・入力させない。
- 将来15分刻み等へ変更できるよう、定数 `WORK_TIME_STEP_MINUTES = 30` でハードコードを避けた構造。

### 概算時刻（〜頃）の保持
- 2026-09-17の稼働開始（本人記録「9時頃」）のように、厳密な分が確定していない時刻は `isApproximate: true` として保持。
- 画面上には「09:00頃」のように表現し、実質稼働時間および実質時給にも「（概算）」を付与。

## 3. 距離指標の整理

1. **Uber表示配達距離（主要指標）**
   - 配達明細に登録された確認済み距離（例: 5.58km）の合算値。全件揃っていない場合は `（1/7件）` のようにカバー率を表示。
2. **空走距離（主要指標）**
   - 配達案件間の移動や帰還走行の距離。
   - 現時点では自動実測・確定データが存在しないため、**推測補完せず「算出不可」** として表示。
3. **拡張性**
   - 将来的に走行ログ等が得られた場合に備え、内部データモデル上は `totalActualDistanceKm = uberDeliveryDistanceKm + deadheadDistanceKm` の計算構造を保持。

## 4. 地雷（原則回避）データベース

### 原則回避ポリシー
「絶対拒否」ではなく**「原則回避」**。
すでにそのエリア内に滞在しており、短距離・高効率で完結する案件などは例外として受注可能。

### 3段階評価ステータス
- ⚠️ **確定地雷 (AVOID)**: 実走や立地条件から明確に稼働効率を破壊すると判断された案件・スポット。
- 🔍 **地雷候補／要検証 (VERIFY)**: 報酬額は高いが所要時間・移動導線の負担が大きいなど、判断が分かれる案件。
- ✅ **問題なし (OK)**: 検証の結果、効率的に受注できると確認された案件。

### 実走事例の蓄積
- 自身の配達実走経験をもとに、案件ごとの所要時間、長大橋・階段、入館導線、帰路空走リスク等の実態を蓄積。
- 登録データはSupabaseのRLS保護により、本人のみが参照・更新可能。端末内LocalStorageとの双方向同期に対応。

## 5. 分析画面の仕様

1. **今週の売上ヒーローカード（最重要）**
   - 次回振込対象の当週公式正本売上（¥17,080）を最前面に表示。
2. **先週比較の安全な構造**
   - 先週の確定データが存在する場合のみ、`先週比 +¥○○○`（明るい暖色系）または `先週比 -¥○○○`（明るい青系）を小さく表示。
   - 先週データが不足している場合は、推測・捏造せず「先週比：比較データ未登録」と控えめに表示。
   - 将来週データが蓄積されれば完全自動で比較計算が行われる。
3. **日別実績の日付・曜日自動判定**
   - `2026/09/14（月）` のように曜日付きで表示。
   - 曜日文字のみを視覚的に区別（平日: 通常色、土曜: 明るい青系、日曜: 明るい赤〜ピンク系）。
   - 日本の祝日（`JAPAN_HOLIDAYS` 辞書構造）も日曜日と同系統でハイライト可能。データ未登録日は推測判定しない。
4. **正本・明細突合監査**
   - 正式売上 17,080円、明細集計 17,084円、要確認差額 +4円を画面最下部の控えめな灰色フッターに表示。架空の調整レコードは作成しない。

## 6. 将来展開・商品化に向けたデータ分離規約

他都市（東京、福岡、名古屋等）への展開や汎用プロダクト化を見据え、以下の分離規約を遵守します。

1. **コアロジック層 (`js/store.js`, `js/ui.js`, `js/app.js`)**
   - セッション計算、時給算出、空走ロジック、3段階評価判定、週次集計、曜日判定等は完全汎用。
   - 特定の地域名や特定店舗名をハードコードしない。
2. **マスターデータ・シード層 (`seed/` or 初期DB設定)**
   - 地域依存の回避方面や実走事例は、マスターデータ（`AVOIDANCE_DATABASE`）またはSupabaseテーブルとして独立定義。
   - 他地域展開時は設定データのみを差し替えるだけで動作する。

## 7. 起動方法

### Windows BAT起動（推奨）
デスクトップの **`UBER_LOG起動.bat`** をダブルクリックするだけで、既定のブラウザで高速起動します。黒いコンソール画面は残りません。

### ファイル直接起動 (`file://`)
`index.html` を直接ブラウザ（Edge / Chrome / Safari）で開いても、CORSエラーやESモジュール制約を受けないクラシックスクリプト形式を採用しており、コンソールエラー0件で完全動作します。

## 8. 配達マップ（ピックアップ店舗）

`pickup-map.html`（UBER LOG 下部ナビの「🗺️ 地図」から開く。地図ページ左上の「← UBER LOG」で戻る）。`js/store.js` の配達実績を開くたびに店舗単位で再集計し、事前調査して固定保存した住所・緯度経度で実地図（国土地理院 地図タイル／OSM 切替）にピンを立てる。地図表示時に外部ジオコーディングはしない。

- 店舗マスタ正本: `data/uber_pickup_stores.json`（`name_keys` が表記ゆれの統合ルール。座標未確定は `coordinate_status: needs_review` で座標なし）
- ブランド・カテゴリ: `data/uber_brands.json`（チェーンの別名・表示名の統一（例: ケンタッキー→KFC）・読み・カテゴリ。新店舗も自動でブランド判定され、名称順でブランドごとにまとまる。同じ住所の店舗は店舗マスタの `sites` で「同一拠点」として関連付け、回数は店舗ごと）
- 重要地点・ルート: `data/uber_map_points.json`（安治川トンネル・安治川大橋。`routes` に避けたいルート等を追加可能）
- 再集計・検証・出力: `node tools/pickup-map/build-stores.js`（`--check` 検証のみ / `--verify-geo` 国土地理院逆ジオコーダで区・町名を再確認）
- ナビ: 店舗詳細（ピン・検索候補・ランキングのどこから開いても同じ）の「🚲 現在地から自転車で行く」で Google Maps を開く。目的地は店名ではなく保存済み緯度経度、出発地は指定せず Google Maps 側の現在地、`travelmode=bicycling`。座標未確認の店舗はボタンを出さず「座標未確認のためルート案内できません」。iPhoneのホーム画面アプリ表示では Google Maps アプリ（`comgooglemaps://`）を先に試し、開かなければウェブ版へ切り替える。
- 現在地: 地図左上の「◎」を押したときだけ1回取得（常時監視なし）。拒否されても地図は通常どおり使える。
- テスト: `node tools/pickup-map/spec/pickup-map-tests.js`（単体）／ `node tools/pickup-map/spec/pickup-map-e2e.js`（Edge で iPhone相当 320/360/390/430px を実際にタップして確認。ネット接続が必要）

## 9. ルート判断マップ（🧭 ルート）

`route-judge.html`（UBER LOG 下部ナビの「🧭 ルート」）。案件（現在地 → PICK → DROP）が安治川を越えるか、越えるならどの横断ポイントが近いかを確認する。店舗の配達マップ（🗺️ 地図）とは別画面。

- 操作: 「PICK」を押して地図をタップ → 自動で「DROP」に切り替わるので地図をタップ（ドラッグで調整可）。「🏪」で店舗マスタの店を PICK にできる。「◎」で現在地（押したときだけ1回取得）。案件は端末内に保存され、「↺」でクリア。
- 地理データ正本: `data/uber_route_geo.json`（OSM の堂島川・安治川の中心線、横断ポイント4か所の入口座標、将来の注意地点 `cautions` の枠）。変更後は `node tools/route-judge/build-geo.js` で `data/uber_route_geo.js` を再生成。
  - 安治川トンネル: 南口（西区安治川一丁目）／北口（此花区西九条二丁目）、立坑エレベーター
  - 安治川大橋（国道43号）: 橋の歩道＋両端のスロープ付き階段（南: 港区波除六丁目／北: 此花区春日出南一丁目）。**⚠ 自転車押し歩きあり**
  - 天保山渡船・上流回り（中之島西端）: 参考
- 計算: `js/route-judge-core.js`（岸の判定・横断判定・横断ポイント別の直線目安距離）。道路の経路計算ではない。
- テスト: `node tools/route-judge/spec/route-judge-tests.js`（単体）／ `node tools/route-judge/spec/route-judge-e2e.js`（Edge で iPhone相当 320/360/390/430px を実際にタップ）

## 10. 地雷タブ: DROP先照合（タワマン等）

Uber Driver に案件が出ている数秒間に、DROP先のマンション名・町名・住所を照合する（サブ端末の iPhone で使う想定）。下部ナビ「地雷」を開くと最上部に表示。従来の地雷DB（原則回避ポリシー・実走事例の3段階評価・Supabase同期）は同じタブの下に「📋 実走事例・地雷DB（従来）」として折りたたんで残している。

- データ: `data/uber_drop_buildings.json`（正本）/ `.js`（ブラウザ用）。Excel「大阪市_タワマン一覧_Uber配達用.xlsx」から `python tools/drop-check/import_excel.py [Excelのパス]` で生成（Excel は読み取りのみ。区別集計シートと件数照合。再取込しても本人評価 `my` は引き継ぐ）。読みは `tools/drop-check/readings.json`。
  - Excel に無い物件（浪速区8件）は `tools/drop-check/additions.json` に書き、取込時に Excel の後ろへ合流（Excel は変更しない）。名称・所在地・階数は2つの公開情報（tawaman.jp・tower.ne.jp）で一致したものだけ、番地が確認できないものは丁目まで、町名の読みは郵便番号データで確認。一般目安は付けない。Excel の物件と同名（表記ゆれ込み）・同番地なら取込を中止。
- 位置づけ: 「配達に時間がかかる可能性があるため確認したい物件」。Excel の「Uber目安」（一般目安）・階数・備考・情報源はデータに残すが、現場画面（一覧・詳細）には出さない。
- 一覧: 1件2行（左上＝物件名、左下＝区 町名丁目、右上＝「詳細評価」、右下＝本人評価の丸アイコン）。評価は丸アイコンだけ（⚪未検証／🟢／🟡／🔴、文字は出さない）。
- 区ボタン: ［全］［西］［此花］［港］［福島］［浪速］［北］［中央］［他］（配達で使う順・表示だけ「区」を省略。絞り込み・検索・件数表示は正式な区名）。390px 以上は横スクロールなしで1列、それより狭い画面は横スクロール。並びと短い名前は `js/drop-check-core.js` の `WARD_ORDER` / `WARD_SHORT`。
- 表示順: ［名前順］（五十音順）／［評価別］（🔴避けたい→🟡注意→🟢問題なし→⚪未検証 の見出しごと、各グループ内は五十音順、該当0件のグループは出さない）。区ボタン・検索と併用。順番は `js/drop-check-core.js` の `RATING_GROUP_ORDER` で変更。選択は端末の localStorage `uber_drop_view_v1`（本人データとは別キー）に保存。
- 本人評価・本人メモ: 「詳細評価」で所在地と 🟢問題なし／🟡注意／🔴避けたい・本人メモだけを表示（初めて付けた時点で本人確認済み）。「⚪ 未検証」は評価ではなく評価が無い状態。「未検証に戻す」は小さなリンクで2回押し。本人メモは1行・20文字まで（保存ボタンまたはキーボードの完了）。
  - 保存先: **端末のみ**（localStorage `uber_drop_personal_v1`、物件 id ごとに rating / note / tags[将来の理由タグ] / 日時 / 物件名の控え）。Supabase には同期しない（別端末・ブラウザのデータ消去では引き継がれない）。将来は `uber_metadata` の1キーとしてテーブル変更なしで同期できる形。
  - Excel 再取込: 基礎データ（`data/uber_drop_buildings.*`）に本人データを持たないので消えない。取込時は前回の id を引き継ぐ（同じ名前、または同じ区・所在地が1件だけ一致）。万一 id が変わっても本人データに控えた物件名で付け直す。
- 検索: マンション名・読み・区・町名（読み含む）・住所・階数・備考。全角半角・カナかな・空白・曾/曽を吸収、複数語は AND、区名を含む入力（「西区ライズ」）は区で絞る。区ボタン（同じ区を再タップで解除）。読みのあいうえお順。
- 音声: 専用ボタンは無し。検索欄をタップして iPhone キーボードのマイク🎤で話すと、入力された文字でそのまま即時検索される。
- 検索欄の属性: `type="search"` `name="dc-search"` `autocomplete="off"` ほか。iPhone の「連絡先を自動入力」を出しにくくするため、name・placeholder・ラベルに「名前」「住所」等の語を使わない（Safari は `autocomplete="off"` を無視するため完全には抑止できない）。
- データ管理（バックアップ）: 地雷タブの一覧の下「🗄️ データ管理（バックアップ）」（普段は閉じた1行）。この端末・このアプリの `uber_drop_personal_v1` を **読むだけ** で JSON に書き出す（`js/drop-backup.js`）。localStorage の変更・削除・統合はせず、Supabase とも通信しない。復元（インポート）機能は無い。
  - 形式: `{ backup_schema: "uber_drop_backup/1", exported_at, exported_at_utc, app_version, device_memo, user_agent, display_mode, page_origin, source_storage_key, source_present, source_item_count, source_parse_error, source_read_error, source_data（保存内容をそのまま解釈したもの）, source_raw（保存されている文字列そのもの） }`
  - ファイル名: `uber_drop_backup[_端末メモの英数字]_YYYY-MM-DD_HHMM.json`。0件（保存なし）でも書き出せる。iPhone で共有シートが使える場合は「共有して保存」から「ファイルに保存」も可。Safari とホーム画面アプリは保存が別なので、それぞれで書き出す。
- テスト: `node tools/drop-check/spec/drop-check-tests.js`（単体）／ `node tools/drop-check/spec/drop-backup-tests.js`（バックアップ単体）／ `node tools/drop-check/spec/drop-check-e2e.js`（Edge で iPhone相当 320/360/390/402/430px）／ `python tools/drop-check/import_excel.py --check`（データが Excel と一致）
